# 01 · 认识 quickmud

> **本章你会学到**：quickmud 解决什么问题、它的心智模型、三条必须记住的铁律，
> 以及"引擎不内置领域内容"的分层哲学。不写代码。

---

## 传统写法会死在哪

写文字冒险游戏，难点从来不是"打印一段描述"，而是**状态一旦复杂起来就再也收拾不住**：

- 存档无从下手——状态散落在几十个变量里，序列化无从谈起；
- NPC 行为和玩家操作互相踩——谁都能改状态，出 bug 没有第一现场；
- 出了 bug 无法复现——"刚才那轮发生了什么"永远说不清。

quickmud 的解法是把游戏拆成一条**单向流水线**，并让整条流水线**确定性可重放**——
于是存档、回滚、录像、AI 预演都变成了同一件事的副产品。

## 心智模型：一条单向流水线

玩家敲下 `attack 野狼` 之后发生的事：

```
玩家输入 "attack 野狼"
      │
      ▼
┌─ 命令 (Command) ─┐   解析动词和参数，只负责"翻译意图"
│  emit(Attack)   │   发出一个事件，不做任何具体逻辑
└────────┬────────┘
         ▼
┌─ 事件泵 (EventPump) ─┐  按优先级派发给订阅者
└────────┬────────────┘
         ▼
┌─ 系统 (System) ──┐   唯一允许修改状态的地方
│ 扣血 → 判死 → 掉落 │   多个系统可对同一事件各司其职
└────────┬─────────┘
         ▼
┌─ 输出 (OutputCollector) ─┐  所有给玩家看的文字都汇到这里
└──────────────────────────┘
```

**三条铁律**，记住就够了：

1. **命令不改状态，系统不解析输入**——命令只 emit 事件（输出除外），系统只消费事件。
2. **状态只活在组件里**——实体（Entity）只是个 ID，数据全挂在组件（Component）上。
3. **所有玩家可见的文字走输出收集器**——不要在系统里 `console.log`。

为什么要这么绕？因为**状态集中**才可能做快照存档，**事件驱动**才可能做回滚、录像、
多事件联动。前期觉得绕的地方，后期都会还你自由。

## 分层哲学：引擎不知道什么是"房间"

| 包 | 职责 | 边界 |
| --- | --- | --- |
| `@mud/ecs-engine` | **能力原语**：事件驱动 ECS、确定性、快照/回滚、录像重放、对话机制 | 不知道什么是"房间"或"背包" |
| `@mud/prefabs` | **领域常用件**：移动/房间/地图、物品、战斗、任务、Buff、对话 | 换一个游戏直接复用，不必从示例抄代码 |

换一个游戏，引擎不用动；想换个玩法规则（比如 Roguelike 回合制），prefabs 可以整个不用。

## 设计取舍（值不值得用，看这五条）

- **确定性优先于便利**。引擎内禁用 `Math.random` / `Date.now` / `crypto`（ESLint 强制）——
  需要随机就自己注入种子，需要时间就走 `clock`。换来的是录像重放和世界分叉。
- **冲突在定义期 fail-fast**。房间重复 id、悬空出口、坐标撞格、组件 ID 哈希碰撞，
  宁可启动时崩溃，也不运行时静默出错。
- **零第三方依赖**。运行时与编译期都不依赖外部包；ESM + CJS 双产物，Node.js ≥ 18。
- **暂不支持**：i18n、数据驱动内容加载（YAML 等，内容当前内联在代码中）、多人联网。
