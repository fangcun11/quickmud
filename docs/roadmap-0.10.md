# v0.10.0 设计定稿：用真内容吃满 v0.9（example/tide-cellar）

- 日期：2026-09-04 · 基线：v0.9.0（engine 0.6.0 / prefabs 0.7.0）
- 状态：**已实现**（v0.10.0，prefabs 0.8.0；实现记录见 CHANGELOG 0.10.0 条目）
- 主题：**内容验证版**——v0.9 的 API 面里有一半只有单测、没有真实世界在用；
  本版做一个真正吃满它们的内容包，把"未验证的 API"变成"有消费者的 API"
- 起点：v0.9 发版后对账发现——`canEnter`/`canLeave`/`on.leave`/`on.look`/`on.every`/
  跨层区域/区域实体状态**真实内容零使用**

---

## 一、为什么要做一个内容包（而不是继续加能力）

引擎的哲学一直是"等真实内容逼出需求"。v0.9 一口气加了区域与房间行为两层能力，
但只有 mini-rpg 一个消费者，且它只用到了其中一半：

| v0.9 API | 单测 | 真实内容 |
| --- | --- | --- |
| `defineArea`/`layoutWorld`/`buildAreas`/`worldmap` | ✅ | ✅ mini-rpg 三区域（**平面串联**） |
| `on.enter`/`firstEnter`/`state`/`commands` | ✅ | ✅ 毒雾/蛛巢/洞穴 search |
| 守卫 `canEnter`/`canLeave` | ✅ | ❌ |
| `on.leave`/`on.look`/`on.every`（房间心跳） | ✅ | ❌ |
| 跨层区域（`up/down` 分成独立区域） | ✅ | ❌ |
| 区域实体挂自己的组件（状态载体） | ✅ | ❌ |

**只有单测的 API 严格说还没做完**——单测证明"它按我写的那样工作"，
真实内容才能证明"它按内容作者需要的那样工作"。本版不追求新能力，
追求把这半张表点亮，并顺带逼出缺口清单里真正该做的那一项。

> 澄清一个此前担心、查证后不成立的点：v0.9 把"行为是代码"搬进 `defineRoom`，
> 并没有打破"状态全在组件 ⇒ 整世界可序列化"。自定义系统（如 mini-rpg 的
> `SpiderRevengeSystem`）从来就是代码、从来不进快照——**行为代码与内容系统
> 代码地位完全相同**。录像重放存的是输入序列 + `engineVersion`，重放时用当前
> 代码重跑，语义未变。

## 二、场景：潮汐地窖（tide-cellar）

三层三区域，用 `up`/`down` 跨层——这正是 v0.8 装不进二维平面、v0.9 才解决的场景：

```
钟楼 belfry(C)          stair ─up─► bellroom（显式 coords，见下）
                          ↑ up
地面 ruins(A)    nave ◄─west─ courtyard ─east─► well
                                                  │ down
地窖 cellar(B)   steps ─south─► cistern ─east─► altar
                  └─east─► valve
```

- **A 地面废墟**：`courtyard`（入口/庭院）、`well`（井口，down 入口）、`nave`（礼拜堂，up 入口）
- **B 地窖**：`steps`（台阶）、`cistern`（蓄水池）、`valve`（闸门房）、`altar`（祭坛）
- **C 钟楼**：`stair`（旋梯）、`bellroom`（钟室）

坐标：A/B/C **各一张独立平面**（v0.9 核心）。注意 `stair ─up─► bellroom` 是
**区域内部的跨层边**——`up/down` 不进平面，bellroom 会拿不到坐标，因此给它
`coords: { x: 0, y: -1 }` 显式钉住（escape hatch，正好演示它存在的理由）。

## 三、机制清单 ↔ API 覆盖

| 机制 | 用到 | 说明 |
| --- | --- | --- |
| **潮汐水位** | 区域实体组件 + 区域级系统 | `Tide { level, rising, valveShut }` 挂在 **cellar 区域实体**上，由 `TideSystem`（every 4000ms）推进——**跨房间机制归区域，不归房间**（v0.9 边界铁律） |
| 蓄水池封路 | **守卫 `canEnter`** | `cistern` 水位 ≥1（没退干）拒绝进入，输出理由 |
| 退路被淹 | **守卫 `canLeave`** | `steps` 水位 ≥3 只封 `up`（守卫拿得到 `direction`）——地窖内部照走，制造"涨潮前必须出来"的时间压力 |
| 蒸汽阀 | **房间 `on.every`** | `valve` 每 3000ms 喷一次，玩家在房内受伤——纯房间局部周期，与潮汐的 4000ms 独立运作（验证两个周期互不干扰）；读房间 `state`，关闸即停 |
| 祭坛烛火 | **`on.leave`** | 带着祭器离开 altar 时触发 |
| 墙上刻痕 | **`on.look`** | `altar` 的刻痕随**当前水位**显示不同内容（房间读区域组件） |
| 初见祭坛 | `firstEnter` | 首次进入描写 |
| 关闸门 | **房间命令 + `state`** | `turn` 关闸（只生效一次，`state` 记账），写区域 `Tide`——演示房间命令的系统特权。**闸门是"换区间"不是放水**：水位锁死在 1，退路保住、蓄水池照样进不去 |
| 敲钟 | 房间命令 + `state` | `ring` 强制退一格——从 1 退到 0 开出一个**几秒的窗口**，水一回来门又关上（测试显式验证"窗口开了又关"） |
| 取祭器 | 房间命令 + `state` | `pray` 得到祭器，spawn 出来的东西真捡得走 |
| 终局 | 全局系统 | 拿祭器回到 `courtyard` → 通关（`Ending` 实体记账，只结算一次） |

## 四、边界（本版刻意不做的事）

- **潮汐不塞进任何一个房间**：它影响四个房间，属于区域（`Tide` 挂在区域实体上，
  `TideSystem` 是全局系统）。房间只通过 `canEnter`/`canLeave`/`look` **读**水位
- **不新增 prefabs 能力**：本版的目标是验证，不是扩张。若真实内容逼出缺口，
  记录到缺口清单，交给 v0.11
- **不改 mini-rpg**：它是完整的通关叙事（7 幕闭环），塞机制进去会毁掉叙事完整性

## 五、验证门

`example/tide-cellar/src/content.test.ts`（测试即通关录像，真实 World + 手动 `tick()`）：

- ✅ 出生点：`map` 带【废墟】抬头（区域过滤）、`worldmap` 三区域剖面图
- ✅ **跨层移动**：`down`/`up` 往返三个区域，位置与区域归属都对
- ✅ **守卫拒绝**：水没退干进不了蓄水池（不落位、输出理由）；涨到顶出不来（`canLeave` 只封 `up`）
- ✅ **房间命令**：关闸门/敲钟改变区域水位（跨实体写生效且只生效一次——`state` 记账）
- ✅ **房间心跳**：在闸门房内推进时间会受伤（3 tick 恰好一次，无漂移），关闸后停
- ✅ **`on.leave` / `on.look`**：离开祭坛触发烛火、看刻痕随水位变化
- ✅ **敲钟窗口**：敲完等 8 秒水位回 1，同一条路又被拦下——窗口机制被显式测试
- ✅ **通关**：趁窗口进蓄水池 → 取祭器 → 回地面终局（只结算一次）+ 潮汐节奏独立断言
- ❌ **prefabs/engine 零改动——没有成立**：内容玩一遍撞出两个真缺陷（见下）

## 五·五、真内容撞出来的 prefabs 缺陷（已修，prefabs 0.8.0）

这正是做内容包的意义——单测只能证明"按我写的那样工作"，玩一遍才知道
"是不是人用的东西"：

1. **撞墙文案中英混杂**：`MovementSystem` 输出「你不能往up走。」——方向 id
   被原样拼进中文句子，而 `roadmap-0.9` 的流程图里写的一直是"你不能往北走"。
   修：`directionLabel()`（north→北、up→上……，未知方向退回 id 本身）
2. **世界地图首部空行**：`renderAsciiMap` 只裁尾部不裁首部，纵向叠层的三层
   剖面图头顶挂着两行纯空白。空行不带字形，裁掉不影响已探明内容的相对位置
   ——只裁尾部是不对称的漏裁，不是设计。修：首尾都裁，中间照旧保留
